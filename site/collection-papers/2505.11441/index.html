Is Compression Really Linear with Code Intelligence?

压缩能力与代码智能真的线性相关吗？

Paper Collection · World Models · 原文

作者信息

Card 02 研究问题

研究问题

  • 语言模型的压缩率常被视为一般智能的代理量，但代码含多语言、多任务和严格输出格式。论文问：在公平激发预训练模型能力后，未见 GitHub 代码上的 bits-per-character BPC 与代码 benchmark 表现是线性还是其他函数关系？
  • 若格式错误被当作能力失败，不同 instruction tuning 会污染比较。作者因此把 intrinsic capability 与 format compliance 分开。
Card 03 背景

背景

  • 对自回归模型，BPC 是字符归一化的负对数似然，越低表示压缩越好。它依赖 tokenizer、context window、滑窗 overlap 和验证语料分布，不能脱离协议比较。
  • 所谓线性 compression–intelligence 可能只是在有限 BPC 区间观察某条非线性曲线的尾部；扩大模型家族与任务覆盖才能区分函数形式。
Card 04 模型与方法

模型与方法

  • 作者构建大规模、未见的多语言 GitHub validation set，用 sliding-window BPC 消除不同 context length 带来的截断优势，并报告开源与闭源语料两套估计。
  • OmniCodeBench 汇总代码生成、修复、推理和解释，覆盖多种编程语言。Format Annealing 是轻量训练，只教统一响应格式、减少空字符串，不意图注入新的代码知识。
  • 对多类开源 Code LLM 计算 BPC 和 annealed benchmark score，比较原始线性拟合与对 intelligence 取对数后的关系，并按任务和 Python/SQL 分层。
Card 05 核心结果与证据

核心结果与证据

  • Figure 3 在开源验证集上给出 log(intelligence) 与 BPC 近线性关系，Pearson 约 -0.956、RMSE 5.7%；等价地，原尺度 intelligence 随压缩改善呈指数/对数曲线，而不是全范围直线。
  • 闭源验证集 Figure 4 给出相似趋势；Figure 5/6 显示不同任务与语言仍大致遵循该关系，但散点和斜率并不完全相同，说明聚合标度不是无条件 universal law。
  • 附录 Figure \(B_{1}\) 的原尺度线性拟合 RMSE 0.115，高于 log 关系的 0.057。Format Annealing 显著减少空输出，使 benchmark 更接近模型能否完成代码任务，而非是否掌握模板。
Card 06 有效性与局限

有效性与局限

  • 相关性不证明压缩导致代码推理能力；两者都可能随模型规模、训练 token、数据质量或架构共同变化。模型点数、家族聚类和同源训练数据会让普通 Pearson 置信度过于乐观。
  • BPC validation set 虽去重并声称未见，仍难完全排除 GitHub 语义重叠；Format Annealing 也可能改变能力而不只格式。benchmark 聚合与 log 变换选择影响函数结论。
  • 关系主要覆盖已有开源 Code LLM 的 BPC 区间，不保证外推到更强模型或新语言。该卡 no independent reproduction performed。

Card 08 阅读指南

阅读指南

  • 先看 Figure 3/4 的坐标轴确认 intelligence 已取对数，再读 Appendix B 的原尺度线性残差；然后检查任务/语言分层是否支持同一斜率。
  • 物理上更像有限动态范围内的 equation of state：经验 collapse 有用，但若没有控制隐变量和独立外推检验，不能升级为普适标度律。
